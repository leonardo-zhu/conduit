# 自建网关：背景、需求与重构计划

状态：进行中。管理后台前端已完成（假数据），数据库、管理接口和网关数据面待做。标「待确认」的条目需要先定下来。

## 背景

Conduit 现在由两部分组成：

- **NewAPI**（官方镜像）：负责令牌、额度、渠道、模型重定向、日志和管理后台。
- **adapter**（本仓库，Bun）：把 Responses 协议转换成上游的 Chat 协议，作为 NewAPI 的一个渠道。

它服务多个自己的应用，Vita 是第一个接入方。上游是 Ark（火山方舟 Agent Plan）、MiniMax、Nous，其中 Ark 是订阅制套餐。部署在 R4S 上，和其他十来个容器共用约 4GB 内存。

接入 Ark Agent Plan 时遇到了问题：NewAPI 的火山引擎渠道类型不认识 Agent Plan 的地址，最后靠“自定义渠道 + 路由表”绕过去。这件事本身不致命，但让我们重新审视了一个问题：**我们到底用了 NewAPI 的哪些功能。**

结论是：实际只用了它很小的一部分（约 20%），而它的大部分体量（注册登录、充值兑换、价格倍率、多 key 轮询、各种格式互转等）和我们的场景无关。同时它没有“应用”的概念，要靠“用户 + 令牌”的约定来映射。

资源方面不是动因：NewAPI 实测只占约 70MB 内存，Conduit 整体约 87MB。

## 为什么要自建

- 需求小而明确，自建的范围可控。
- 想要一个贴合“应用 / 设备 / 模型别名”的模型，而不是靠约定去适配通用网关。
- 上游适配（比如 Agent Plan）完全由自己掌握，不用等别人的版本。
- 协议转换已经在 adapter 里，合并之后只有一个服务，部署更简单。
- 不再被一个功能很多、更新很快的外部项目牵着走。

代价也要认：管理后台、用量对账、令牌安全这些都要自己维护。

## 需求

### 必须有

1. **应用与设备令牌**：每个应用、每台设备各有令牌；支持过期、禁用、限定可用的模型。
2. **额度**：每个应用有总预算，每个令牌有上限。只做“用量计数”，不做价格和计费，因为上游是订阅套餐。
3. **用量记录**：能按应用、令牌、模型查看；流式请求的用量必须准确。
4. **模型别名**：应用只使用别名，更换上游模型时只改配置，应用不用发版。
5. **上游管理**：配置 Ark、MiniMax、Nous 等上游的地址和密钥，别名对应到上游。
6. **协议支持**：对外提供 Responses 接口（现有约定），也要能提供 Chat 接口；Responses 和 Chat 之间的转换沿用现有 adapter 的逻辑。
7. **管理后台**：能创建应用、令牌、别名和上游，查看用量。
8. **自定义首页**：沿用现有的首页，直接由新服务托管。

### 不需要

用户注册与登录（只有管理员自己）、充值与兑换码、价格倍率与分组计费、多 key 轮询、渠道优先级和权重、自动重试和渠道自动禁用、Claude 和 Gemini 格式互转、图片、音频及其他多媒体能力。

### 暂不做，视情况再加

- 同一别名对应多个上游的备用切换。
- 用量告警、周期报表。
- Claude 格式（`/v1/messages`）的接入，等有客户端需要时再评估。
- 管理员登录的 TOTP / Passkey。

## 总体方案

- 用 **Next.js 16**（App Router）做成一个单体服务，代码在 `web/`，同时承担网关接口和管理后台，沿用个人站已经跑通的镜像构建和 R4S 部署方式。
- **管理后台界面取自 NewAPI 前端**，删减到上面的需求范围。NewAPI 是 AGPL-3.0，`web/` 随之以 AGPL 发布：保留原文件版权头、`web/LICENSE` 和 `web/NOTICE`，界面侧边栏保留署名和原项目链接，修改记录见 `web/README.md`。
- 网关的核心逻辑（令牌、额度、别名、转发、用量）与框架解耦，接口层只做很薄的一层，这样以后如果在代理路径上遇到框架问题，可以单独拆出去。
- 数据存放在本地 SQLite，量很小（现有 NewAPI 数据不到 1MB）。优先用 Node 内置的 `node:sqlite`，避免原生模块在 ARM 上交叉编译（待验证）。库在 TF 卡上：开 WAL，用量记录批量写入。
- 现有的协议转换逻辑迁移进来，adapter 独立容器最终合并掉。
- 目标资源占用：不明显高于现在的 Conduit 整体，约 100 到 150MB 以内；以上线后实测为准。

## 关键设计

### 数据模型

| 对象 | 主要字段 | 说明 |
|---|---|---|
| 应用 | 标识（如 `vita`）、显示名、额度、周期、已用、状态、备注 | 预算和隔离的单位 |
| 令牌 | 所属应用、名称、密钥哈希与前缀、状态、过期时间、额度上限、已用、可用别名、IP 白名单、最近使用 | 一台设备或一个服务实例一个令牌；明文只在创建时显示一次 |
| 别名 | 所属应用、名称（如 `vita-chat`）、上游、上游模型名 | 按应用隔离，命名约定 `<应用>-<用途>` |
| 上游 | 名称、协议（Responses 原生 / 需转 Chat）、地址、加密的密钥、状态、备注 | 密钥用环境变量里的主密钥加密后存库，后台只显示末四位 |
| 用量记录 | 请求 ID、应用、令牌、别名、上游与上游模型、输入 / 输出 token、是否流式、状态码、错误类型、首字延迟、耗时、是否估算、时间 | 只记元数据，不记请求和响应内容 |

后台界面目前沿用 NewAPI 的接口格式（应用对应“用户”，上游对应“渠道”，别名映射挂在渠道上）。写真实接口时按上表改，页面跟着调整。

### 额度口径（2026-10-29 按此实现）

- **单位**：token（输入 + 输出）。同时记录请求次数，用于和上游对账。
- **周期**：应用的额度可以设周期：不重置，或者每月 1 日重置。默认不重置。令牌的额度暂不分周期，需要时再加。
- **扣减**：请求开始前检查应用和令牌都还有余额（不预占）；请求结束后按上游返回的 usage 扣减。所以额度用尽前的最后一个请求可能会超出一点，单人使用可以接受。
- **流式与断开**：以上游返回的 usage 为准。客户端中途断开时立即中止上游请求；拿不到 usage 时按已收到的输出估算，并在记录上标“估算”。
- **并发**：单进程，扣减在 SQLite 事务里完成，同一令牌的并发请求不会少扣。

### 管理员登录

只有管理员一个账号，不建用户表。

- 账号和密码哈希（scrypt）放在服务器的 `.env`（`ADMIN_USERNAME`、`ADMIN_PASSWORD_HASH`），不进仓库。
- 登录成功后发签名的 HttpOnly cookie（`SESSION_SECRET` 签名，7 天有效）。所有管理接口都校验它。
- 登录失败按 IP 限速，防止公网暴力尝试。
- 换密码或让所有会话失效：改 `.env` 里的哈希或 `SESSION_SECRET`，重启服务。

### 从 NewAPI 迁移令牌

NewAPI 库里存的是令牌明文。迁移时把现有令牌导入新库（只存哈希），格式保持 `sk-...` 不变，归到对应的应用下。这样切换时只需改入口地址，Vita 不用换令牌，也不用发版。

## 重构计划

分阶段推进，每个阶段结束都能独立验证，NewAPI 一直保持运行，直到新服务验证通过。

和最初的计划相比，顺序有调整：先做了管理后台的界面，用假数据把每页的字段定下来，再按界面需要的数据写接口。

### 阶段 0：先让现状可用（进行中）

- 在 NewAPI 上完成 Ark Agent Plan 的渠道配置（已跑通），接入 Vita。
- 观察一到两周，记录实际的痛点，用来校正后面的需求。

### 阶段 1：管理后台界面（已完成，`feat/web-console` 分支）

- Next.js 骨架，NewAPI 前端迁入并删减：登录、概览、数据看板、令牌、使用日志、上游、应用。
- `/api/*` 由 `web/src/mock/` 的假数据应答，按 NewAPI 的返回格式。
- 剩余收尾：错误页的反馈链接、渠道页的残留代码、深色模式和手机端检查、自定义首页迁入。

### 阶段 2：数据库、管理接口和登录

- 管理员登录（见上文），所有 `/api` 校验会话。
- SQLite 建表，实现应用、令牌、别名、上游、用量的管理接口，逐个替换假接口。
- 页面按新数据模型调整：渠道页改为“上游”，令牌的可用别名按应用过滤。
- NewAPI 令牌导入脚本。

### 阶段 3：网关数据面

- `/v1/responses`、`/v1/chat/completions`、`/v1/models`。
- 令牌校验、别名解析、额度检查、转发和用量记录；迁入 adapter 的协议转换。
- 重点验证：流式用量是否准确、客户端断开时是否多扣、同一令牌并发时额度是否正确。

### 阶段 4：部署与并行验证

- Next.js standalone 的 ARM 镜像、compose 服务、CI 改为构建新服务。
- 新服务与 NewAPI 同时运行，使用不同的入口地址，实测内存。
- 先让一个低风险的客户端（比如自己的测试脚本）走新服务，以上游控制台的数据为准对账。
- 再让 Vita 切到新服务，保留 NewAPI 作为回退。

### 阶段 5：切换与下线

- 把正式入口地址指向新服务。
- 观察稳定后，停掉 NewAPI 和旧的 adapter，保留一份 NewAPI 的数据备份。
- 更新 `docs/setup.md` 和 `docs/apps.md`，去掉 NewAPI 相关内容。

## 风险与应对

| 风险 | 应对 |
|---|---|
| 流式转发和用量扣减出错，导致多扣、漏扣 | 阶段 3 单独做验证清单，阶段 4 与上游控制台对账 |
| 令牌和上游密钥的安全 | 令牌只存哈希；上游密钥加密存库，主密钥不进仓库；后台只对管理员开放 |
| 后台暴露在公网，被暴力尝试登录 | 登录限速；会话 cookie 签名且 HttpOnly；必要时在 Caddy 层限制来源 |
| Next.js 在代理路径上不稳定或内存超预算 | 核心逻辑与框架解耦，必要时把数据面拆成独立的小服务；阶段 4 实测 |
| 前端沿用 NewAPI 的接口格式，和新数据模型不一致 | 阶段 2 写真实接口时按新模型改页面，不迁就旧格式 |
| AGPL 的义务被遗漏 | 保留版权头、LICENSE、NOTICE 和界面署名；修改记录写在 `web/README.md` |
| 迁移期间出问题影响 Vita | 全程保留 NewAPI 作回退，切换可逆；令牌迁移后 Vita 不用改配置 |

## 验收标准

- Vita 通过新服务正常使用，包括流式对话和工具调用。
- 用量数据和上游实际调用次数对得上。
- 禁用一个令牌后立即生效，且不影响其他令牌。
- 更换一个别名对应的上游模型，应用无需改动。
- 内存占用不超过上线前约定的预算。
- 文档完整，NewAPI 可以安全下线。
